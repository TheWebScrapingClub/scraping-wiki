# Mobile App Scraping

## Definition

Mobile app scraping is the practice of intercepting the network traffic generated by a mobile app and replicating the underlying API calls in a scraper. Since mobile apps communicate with backends through the same HTTP/HTTPS protocol as browsers, the data they fetch can be captured and reproduced.

## How It Works

The process requires placing a man-in-the-middle proxy between the app and its backend. The proxy decrypts HTTPS traffic (by installing its own certificate on the device) and exposes every request and response in plaintext. The scraper then replicates whichever calls contain the data it needs.

Standard tools used as the MITM proxy: Fiddler Everywhere, Charles Proxy, HTTP Toolkit, Burp Suite, mitmproxy.

The basic flow on Android:

1. Install proxy software on the desktop.
2. Configure the mobile device (real or virtual) to route traffic through the desktop proxy.
3. Install the proxy's CA certificate on the device.
4. Interact with the app and observe the traffic.
5. Identify the relevant endpoints, then replicate them in a scraper.

## Why App APIs Are Often Easier Than Websites

Mobile app APIs tend to have lighter anti-bot protection than the same company's website. Observed reasons:
- The app presents simple HTTP/JSON requests without JavaScript fingerprinting.
- Rate limiting is usually IP-based and manageable with rotating proxies.
- Browser fingerprinting and CAPTCHA challenges are website mechanisms, not API mechanisms.
- During a TWSC consultancy project, an anti-bot that blocked website scraping was bypassed entirely by switching to the app's API.

Additionally, apps often expose data or endpoints that the website does not. Some products are app-only with no web interface. Some endpoints reveal inventory levels, real-time driver locations, or pricing structures not present on the site.

## Certificate Pinning

The main obstacle in mobile app scraping. Certificate pinning is a security technique where the app checks the server's certificate against a hardcoded expected value rather than trusting the OS certificate store. If the certificate does not match, the connection is refused, even if the device trusts the MITM proxy's CA.

Detection is straightforward: if a non-pinned app's HTTPS calls appear in the proxy, everything is working. If the app shows errors or returns no data while the proxy is active, certificate pinning is the likely cause.

### Bypassing Certificate Pinning (Android)

The standard approach uses Frida, a dynamic instrumentation toolkit that injects JavaScript into a running app at runtime. The injected script hooks into the certificate validation functions (e.g., `X509TrustManager.checkServerTrusted`, OkHttp's `CertificatePinner.check`) and forces them to accept any certificate.

Required setup:
- Root the Android device. For virtual devices, RootAVD is the standard tool.
- Install Frida server on the device (`/data/local/tmp/frida-server`).
- Install frida-tools and frida Python packages on the desktop.
- Run the bypass script: `frida -U -f <package_name> -l script.js --pause`

The virtual device workflow for a Pixel 8 with Android 12 (arm64):
```
./rootAVD.sh system-images/android-31/google_apis_playstore/arm64-v8a/ramdisk.img
adb push frida-server-16.4.8-android-arm64 /data/local/tmp/frida-server
adb shell "chmod 755 /data/local/tmp/frida-server"
```

HTTP Toolkit is a simpler alternative that handles certificate installation automatically. For non-rooted devices via ADB, it can intercept non-pinned traffic without Frida. For pinned apps, rooting is still required.

### iOS Certificate Pinning

iOS apps default to trusting user-installed CA certificates for HTTPS, unlike Android (which stopped trusting user CAs for apps targeting Android 7+). If the iOS app does not use explicit certificate pinning, a stock (non-jailbroken) iPhone can be used: install the proxy certificate via Settings > General > About > Certificate Trust Settings, configure Wi-Fi HTTP proxy, and the traffic flows.

If the iOS app uses pinning, a jailbroken device with Frida or Objection is required, which is more complex than the Android path.

## Practical Interception Tools

### HTTP Toolkit
Open-source, cross-platform. Acts as MITM for browser, Android, and iOS. Handles certificate installation automatically for Android via ADB. Can export intercepted requests in multiple languages (Python, cURL, JS). Free tier available; paid plan adds language export options. For browser inspection, it works without opening DevTools, which is useful when sites disable DevTools.

### Fiddler Everywhere
MITM proxy, first TWSC tool used for app traffic interception. Requires manual certificate installation steps on Android virtual devices.

### Charles Proxy
Alternative to Fiddler, used on Ubuntu/Linux setups. Offers a root certificate that can handle some SSL pinning cases. Paid software with a free trial.

## Replicating Captured Calls

Once calls are captured, the typical approach is:
1. Identify which calls contain the target data.
2. Note all required headers, including custom app headers (`channel: mobileApp`, `platform: android`, `appversion`).
3. Identify any token-based authentication and understand the token acquisition flow.
4. Replicate in Python/Scrapy using the same headers and endpoint URLs.
5. Handle pagination by modifying the relevant parameters.

The main difference from web scraping is that mobile apps often include custom non-standard headers that the backend validates. Omitting them can result in 400 or 401 responses.

## What We Tested

- **Off-White app** (iOS, no pinning): Intercepted via Fiddler. Product catalog accessible through internal Algolia-like API. First Lab episode.
- **Tractor Supply Co. app** (Android virtual device, pinned): Pinning bypassed with Frida. JWT token obtained from `initiateApp` endpoint. Product catalog via authenticated calls. The `x-acf-sensor-data` header (Akamai sensor data) was copied from the captured session and reused statically.
- **Tractor Supply Co.** note: Google service calls inside the app could not be fully intercepted even with Frida, as Google services have additional protection layers.
- **HTTP Toolkit on iOS** (non-pinned delivery app): Manual certificate install, Wi-Fi proxy configuration. Requests visible immediately.

## Known Limitations

- Pinning bypass does not always work on the first attempt; different Frida scripts target different pinning implementations.
- Third-party services embedded in apps (Google Maps, Firebase, analytics) often use separate certificate pinning independent of the main app's settings.
- Some apps detect Frida's presence and refuse to launch; obfuscated Frida variants or Magisk modules may be needed.
- API calls reused from captured sessions include device-specific identifiers (`uniqueid`, `mobileuniqueid`). Using these across many scraping sessions may trigger rate limits or anomaly detection tied to device identity.

## Current State (as of 2026-04)

Mobile app scraping is an established technique with a well-understood toolchain. The barrier is certificate pinning, which requires either a rooted Android device or a jailbroken iOS device. HTTP Toolkit has lowered the setup complexity for non-pinned apps considerably. For pinned apps, Frida remains the standard approach on Android.
